# Plasma input checks

MOOSE parses five plasma Physics actions. Some actions now generate
existing solver operator types when their activation parameters are supplied,
while validation-only inputs do not create an equation. The generated DriftDiffusion slice handles FEM electron conservative time and
transport Kernels together; FV heavy-species transport remains Native and is
NOT generated by this option contract.

| Input path under `Physics/Plasmas` | C++ action | What it checks |
| --- | --- | --- |
| `Transport/DriftDiffusion/Continuity` | `Plasma::ContinuityEq` | Species and existing FEM/FV solver variables |
| `Transport/DriftDiffusion/Energy` | `Plasma::EnergyPhysics` | Electron species and existing FEM energy variable |
| `Transport/Chemistry` | `Plasma::ChemistryPhysics` | Unique reactions and one progress name per reaction |
| `Poisson` | `Plasma::PoissonPhysics` | Existing electric potential solver variable |
| `Maxwell` | `Plasma::MaxwellPhysics` | Existing real/imaginary fields, matching variable families and positive frequency |

All actions share the `PlasmaInterface` validation base class. The
`owner_mode` input has been removed. These actions reuse already registered MOOSE solver operator types and
existing physical fields/materials. When explicitly activated, they may add
Kernels/BCs/Materials, but do not introduce a new equation, time law, source
coefficient, boundary physics or numerical parameter. In particular, the chemistry
action verifies the reaction-to-progress name mapping, not the existence,
units or ownership of the underlying rate functors.

To exercise all five actions with a small simulation, supply
`baseline.i` and `valid_all_physics.i`. The latter is intentionally a
minimal demonstration, **not a physical multi-equation plasma model**.

The build uses the fixed image
`ghcr.io/hyungseonsong-plasma/physics-build-base@sha256:2c3352da4f5c1b2ae98475fc01463ad0cdbc6ce7d221ce55055ddea152182008`
and MOOSE revision `9f388366ccf38b9c34542ec5561198249fde0ac9`.

From the repository root on a Docker runner:

```bash
bash experiments/Issue402_plasma_dsl_g1/run_native_binding_smoke.sh
```

The script compiles the real C++ code, accepts valid inputs, rejects invalid
inputs, and compares two small numerical solves. Real S6 400 W / 100 microsecond
replay with these inputs is a separate validation requirement. The existing
S6 input layers and private chemistry data must remain unchanged. No
scientific result is accepted by this input registration alone.


## Connecting existing MOOSE solver objects

Physical *activation* inputs, not transport coefficient names, determine
whether supported solver operators are generated. A validation-only block
without activating parameters does not add terms.

- **Continuity:** `fem_potential` and matched signed charge vectors enable
  `FEMLogMolarTimeDerivative` **and** `FEMLogMolarDriftDiffusion`
  for each FEM species. Generated names use `<species_id>_time` and
  `<species_id>_transport` (for the S6 electron, `e_time` and `e_transport`). The lower-level
  Kernel's `mobility` and `diffusion` Functors are resolved automatically to
  `<species_id>_mobility` and `<species_id>_diffusivity`. The Physics input
  has **no** user `mobility`/`diffusivity` keys. Once the new FEM generator is
  activated, the old explicit electron time derivative must be absent; reaction
  sources, wall and FV heavy-ion terms remain external. No new scientific
  coefficients, FV transport generators or defaults are inferred.
- **Energy:** `rf_heating_material` creates a `MatBodyForce` source
  in an existing FEM electron-energy equation. The material property
  must already have the equation's correct units.
- **Chemistry:** `rate_table_files`, `mean_energy`,
  `electron_number_density`, and `target_molar_concentrations`
  create existing strict-table `PhysicsElectronImpactRateMaterial` objects.
  Reaction source projection remains external.
- **Poisson:** `charge_source_material` creates `Diffusion` and
  `MatBodyForce`. The property must supply `rho/epsilon0`
  for constant vacuum permittivity; variable permittivity is unsupported.
  Optional `ground_boundaries` adds zero-potential conditions.
- **Maxwell:** `reaction_material` and `coupling_material`
  create paired `Diffusion`, `MatReaction`, `MatCoupledForce`
  exactly as in the existing scalar RF input. Optional `imaginary_source`
  and `ground_boundaries` create forcing and zero-field boundary objects.
  Material coefficients must preserve existing geometry, frequency and
  conductivity conventions. Spatially restricted coil sources and RF
  power deposition materials are not generated.

Never activate generated terms when the same existing equation terms
are also declared under `[Kernels]` or `[BCs]`: doing so double-counts
the physics. The `rf_generated.i` versus `rf_explicit.i` comparison
checks that the Maxwell action generates the same solver operator as
explicit MOOSE objects. This is not full S6 scientific parity.

## 2026-11-12 canonical FEM Kernel naming (no factory aliases)

The active header/source are `FEMPlasmaTransport.h/.C`. Registered class/type
names are `FEMLogMolarTimeDerivative`, `FEMLogMolarDriftDiffusion` and
`FEMLogMolarElectronJouleHeating`. The original `PhysicsFEM...` types are
**not** registered and do not have compatibility aliases. The transient
and positive-`dt` guards and conservative time residual remain unchanged.

Original archived S6 source decks retain historical `type` declarations.
The public B/D runners will translate only **disposable staged copies**
to the new type names with separate per-file SHA and conversion counts;
this is not a solver-side alias or production input modification.
The generated-TimeKernel P2 fixture uses `Transient`, since MOOSE does
not provide a `TIME` vector tag to a `Steady` executioner.

## 2026-11-12 e_time completion candidate — scoped change, not scientific acceptance

The source-backed active `ContinuityEq` implementation now generates two
existing FEM operators under the **same** `fem_potential` plus signed-charge
activation contract, with no new user-facing input option:

- `e_time`: `FEMLogMolarTimeDerivative` for `log_e`, assigned the
  exact `plasma` block. Its original Native `ne_time` type computes
  `(exp(u_new) - exp(u_old))/dt` (backward-Euler conservative molar density).
- `e_transport`: the existing
  `FEMLogMolarDriftDiffusion` generator with the same verified
  mobility/diffusivity functors, charge sign and potential.
- `check_integrity` rejects more than one **same-type FEM time** Kernel
  or more than one drift-diffusion Kernel for each generated variable; this
  protects against accidental simultaneous Native and Physics ownership.
- The public `S6-417/D` / `S6-941/D` staging program requires **exactly one**
  source `[ne_time]` with `type = FEMLogMolarTimeDerivative`,
  `variable = log_ne`, `block = plasma`. Only its disposable candidate
  input deletes this block, canonicalizes `log_ne → log_e`, and leaves the
  immutable archived B/C evidence, RF/PID, chemistry, FV ions, wall BCs,
  energy and all other options unchanged. Source/staged hashes and the deleted
  Native block's SHA-256 remain in the migration record. Ambiguous or absent
  time ownership fails **before** scratch-file writes.

**Checks:** source-level ownership/negative tests and the same pinned
`physics-opt` P1/P2 job (including a new duplicate-`e_time` negative fixture)
are mandatory. They are not full numerical equivalence. The previous
400 W / 100 µs S6/D runtime [#43124474950](https://github.com/HyungseonSong-plasma/moose-test-repo/actions/runs/43124474950)
exercised the **prior** implementation, so it does **not** validate this
additional generated time operator. No costly P3 re-run or full B-vs-new-D
scientific/parity claim is implied by this change.

This section supersedes earlier prose describing the FEM time derivative as
necessarily Native-retained for the new D candidate. The archived
single-`ne_transport` migration scripts and frozen inputs stay intact.

## Species-owned DriftDiffusion transport providers (2026-11-10 current rule)

The user-approved canonical Functor names are derived from the solver-safe
species identifier, with case preserved: `e_mobility` / `e_diffusivity`,
`O2p_mobility` / `O2p_diffusivity`, `Om_mobility` /
`Om_diffusivity`, `Op_mobility` / `Op_diffusivity`.
Neither list order nor user-specified coefficient strings define these names.

`ElectronClosureMaterial` and `ElectronTransportLookupMaterial`
publish canonical electron names using the **same AD table closure** that
produces the existing `electron_mobility` and `electron_diffusion` outputs.
The latter are preserved for old native S6 and other inputs. The
`PlasmaChargeTransportMaterial` publishes species-keyed ion aliases
from its **already supplied** ion-mobility and ion-diffusion Functors when
it owns those species. These aliases are unscaled; `rho_diffusivity_<id>`
remains the separate density-weighted FV coefficient and must not be
substituted for `<id>_diffusivity`.

An input must still provide actual coefficient producers. Never fabricate a
missing Functor, silently choose a legacy provider by species name, replace
`D` with `rho D`, or infer values from a constant/Einstein relation.
Existing archived material and P3 B/C coefficient declarations are unchanged.
The stand-alone new-P2 fixture uses explicit `ADGenericFunctorMaterial`
unit coefficients **only as a parser and construction control**, not as
physical S6 parameters.

**Limits:** The generated FEM electron drift-diffusion kernel uses
`e_mobility` and `e_diffusivity`; FVM species identifiers are validated
but their drift-diffusion kernels are not generated. `--check-input`
certifies parsing/object creation, not physical/numerical equivalence.
`SCIENCE_HOLD` and native P3 remain separate.

The subsequent sections describe earlier migration proposals or prior P2
snapshots. In case of an obsolete `fem_mobility`/`fem_diffusion` or user
`mobility`/`diffusivity` sample, this current rule takes precedence for
new optional Physics blocks; do not edit the immutable historical P3 decks.

The archived S6-417/941 heavy-ion coefficients originate in an existing
`ADGenericFunctorMaterial`, not the modern charge-transport owner. The
review-only new-option D overlay therefore instantiates three controlled
`SpeciesTransportAliasMaterial` bridges: O2p from
`ion_mobility/ion_diffusion`, Om from
`negative_ion_mobility/negative_ion_diffusion`, and Op from
`atomic_positive_ion_mobility/atomic_positive_ion_diffusion`.
They forward the **same AD values** to canonical names without rescaling
or changing the original B/C archived material declaration. The electron
aliases are published by the existing electron lookup/closure producer.

## Single-kernel S6 migration (archived, not production)

The completed S6-417 and S6-941 runs contain an explicit `ne_transport`
FEM log-molar drift-diffusion Kernel. The archive-based preparation program
moves **only this one existing Kernel** into `ContinuityEq` and
preserves its name, parameters and `plasma` block restriction.
The original electron time derivative, energy, chemistry, ion FV equations,
Poisson/MultiApps, controls, materials and all wall conditions remain native.

The `fem_kernel_names = 'ne_transport'` input preserves the existing
Kernel identity. During `check_integrity`, the common plasma validation
also rejects more than one same-type FEM Kernel on a variable, including an
accidental native + Physics duplicate.

To prepare separate baseline and candidate **outside the repository**, with
the two original GitHub Actions S6 ZIP artifacts available locally:

```bash
python3 experiments/Issue402_plasma_dsl_g1/prepare_s6_single_kernel_migration.py \
  --archive /private/path/s6_417.zip \
  --archive /private/path/s6_941.zip \
  --output-dir /private/path/s6_migration_review
```

The generated `migration_report.json` proves only the isolated static
source transformation. It does not prove that the new model compiles or
replays the original 400 W / 100 microsecond trajectory. That full native
comparison requires the archived rate tables and pinned original runtime
dependencies. No private chemistry files are committed or published.

The small native regression now includes a **negative test** that provides
native and generated Maxwell kernels simultaneously and requires rejection.
The C++ duplicate guard is intentionally conservative: two kernels of the
same type targeting one FEM variable are rejected even if deliberately
different sources would otherwise be useful. Keep such complex sources
explicit until typed ownership is implemented.

## 2026-11-10 option-first Continuity experiment (separate stacked draft)

This experiment changes only the `ContinuityEq` **input contract** and
internal names, not any Material or Functor registration, source code or
physical coefficient values. The generated lower-level
`FEMLogMolarDriftDiffusion` parameter remains named `diffusion`.
The user-visible **Physics option** is now `diffusivity`; it can still point
to the existing `electron_diffusion` functor. Changing that provider to
`electron_diffusivity` is deliberately deferred.

- Input `variables` and `fem_kernel_names`/`fvm_kernel_names` remain removed.
  **Default solver-state names are canonical**: `log_<species_id>`, e.g.
  `e -> log_e`, `O2p -> log_O2p`, `Om -> log_Om`, `Op -> log_Op`.
  The synthetic `baseline.i` and all active native fixtures use these names
  consistently for Variables, Kernel, boundary, Energy, Poisson and Maxwell.
- **No legacy solver-state option exists in ContinuityEq.** For public S6
  P2 only, immutable B input layers remain byte-for-byte original, while the
  isolated D scratch workspace rewrites its **temporary copies** of the ten
  input layers from `log_ne/log_ni/log_nm/log_nop` to
  `log_e/log_O2p/log_Om/log_Op`, using complete-variable-token matches.
  The independent D sidecar contains no compatibility flag. The migrator
  records original/staged SHA-256 per input and rejects missing source states.
  Stored archives, historical P3 inputs and previous C-only results do not change.
  A D P2 check establishes **input validity only**, not numerical or science parity.
- `generic_four_species.i` is a syntax-only P2 control proving default
  automatic naming for all four species; generated transport is still limited
  to the verified FEM species and charge identities.
- Generated kernel name is fixed to `<species_id>_transport`, so an electron
  kernel is named `e_transport`. In the existing protected S6 migration
  comparison, the old `ne_transport` remains *unchanged*: it is NOT a valid
  proof for the new scheme, and the prepared P3 B/C input decks are untouched.
- `mobility` / `diffusivity` use FEM-first then FVM ordered coefficient
  vectors; `fem_charge_numbers` and `fvm_charge_numbers` must each match
  declared species and known charge signs when generation is activated.
  There is still **no FV transport Kernel generation**. Providing coefficients
  for unimplemented FV physics does not claim FV support or scientific parity.
- A standalone small-input regression tests valid existing-variable binding,
  deprecated user options, missing FV charges, coefficient vector lengths,
  invalid charge signs and FEM/FVM variable-family mismatch. No native result
  may be reported until the exact branch HEAD is built and checked with OCI.

This is a staged API trial only: `SCIENCE_HOLD`, protected-rate separation,
Issue #493 P3 source/inputs, production defaults and PR #491 remain unchanged.

## 2026-11-10 Native failure containment: P0 / P1 / P2 split

The canonical CI now treats these as separate sequential steps for this
option-only source, before any P3:

- **P0 environment preflight (before build):** checks exact Git HEAD, public
  S6-417/941 immutable deck/rate SHA-256 provenance, pinned OCI accessibility,
  read-only `/workspace` binding, root-owned `.jitcache` creation and
  deletion, and host scratch cleanup. A safe JSON status is emitted at
  `evidence/option_s6_environment.json`. This gate must pass *before* the
  expensive Native build.
- **P1 same-job build and tiny regression:** the existing Native source
  compiler and small positive/negative `--check-input` controls are unchanged,
  but now emit `evidence/native_p1_identity.json` with HEAD, OCI digest,
  binary SHA-256 and native build-log SHA-256. The already-built binary is
  reused only within that exact CI job. Cross-run binary caching/reuse is
  **not** accepted without the separately reviewed canonical P1 evidence
  contract; do not treat a previous CI artifact as a trusted executable.
- **P2 full public S6 input:** four independent actual Native input checks
  and per-case outcomes are written atomically *before* workspace cleanup.
  The overall acceptance condition is `P2=PASS`, `cleanup=PASS` and
  `status=PASS`. If all four inputs succeed but host cleanup fails,
  `P2=PASS` remains factual, `cleanup=HOLD`,
  `status=HOLD_INFRASTRUCTURE_CLEANUP` and CI fails closed. This prevents
  post-check cleanup errors from erasing successful parser evidence or being
  misclassified as input/science failures.

The P0/P1/P2 record path, OCI image/source/binary SHA and old source/rate
manifest must match. No P3/P4 execution or scientific approval is added.
Original S6 P3 decks, Material/Functor producers and workflow credentials
remain untouched.
